Writes Xray test cases from a ticket, and nothing else: no spec file, no test run, no check. A case is what a Playwright test of the ticket checks, as steps QA can read (action, data, expected result), named after that test so the two stay linked. `/quality-code:spec` writes the same cases for the tests it writes; this command is for QA when there is no test to write yet. Plain English, short sentences, numbered cards. Show every card and output the way `${CLAUDE_PLUGIN_ROOT}/guides/display.md` says: a section per step, tables, colour marks, and the picker for questions. Every question is asked with the AskUserQuestion picker as display.md says, never as a numbered text card; the text card is only for a client without the tool. End your turn after every card and wait for the answer.

## Rules

- **Where files go.** When the command has ended (after its last card is answered, or its last step when it shows none), follow `${CLAUDE_PLUGIN_ROOT}/guides/save-place.md`: the first run of a project asks once where its files and logs are kept.
- **Run each plugin script exactly as written:** one `node "${CLAUDE_PLUGIN_ROOT}/bin/…"` command per call, with nothing added before or after it (no `echo`, `;`, `&&`, `|` or redirection). The tool result already shows a non-zero exit code. Anything added stops the call from matching its pre-approval and costs a permission prompt.
- **The script writes.** `xray.mjs` numbers the cases, writes the CSV and the per-ticket files, and skips a case that is already there. Never edit those files yourself.
- **Never invent.** An expected result comes from the ticket (its Then, its QA plan) or from the guide's extra probes; a step whose result the ticket does not give has no expected result. Never a value the ticket does not give.
- **Central Context rules.** The company's rules come from its Central Context hub, and step 4 reads it twice before the plan, as `/quality-code:spec` does. First the `central-context` connector searches the ticket's own topic: `search_knowledge` with what the screen under test does in a few English words (`order list filters`, `sign-in form`; English ranks best, even for an Italian ticket), no `domain`, `max_results` 5, and `client_context` the project folder's name, `#` and the key, with no space (`shop#ABC-123`: Central Context refuses spaces; with no repo, the key's project in place of the folder, `ABC#ABC-123`), which Central Context records. One search, never more. Read each hit's summary: a hit that bears on the cases you write is a candidate, and you read it with `get_knowledge_document` (the same `client_context`) before you apply it; a hit that does not, or no hit at all, is dropped. Without the connector, the search is skipped and said so. Then `rules.mjs` reads the testing rules for the frontend side: Central Context's, the plugin's built-in ones (drafts the plugin ships until Central Context publishes them) and, with `centralContext.local` in the config, the team's own. One id is one rule, and where two rules disagree the team's own wins, then Central Context's, then the built-in one. Every list is candidates, never orders: apply only the rules that bear on the cases of this ticket, which is how a case is worded and traced to its ticket, and which of the guide's extra probes fit this screen. A rule about something else (how an automated test is built or run, mutation, coverage, CI) does not apply to a test case: leave it out. A rule never adds a case of its own, never gives an expected result, never outranks the ticket's Then, the QA plan or a team guide, and never changes the gate's score. Never paste rule text into a case or Jira. When nothing is read (the hub is off, or it does not answer), go on without: the rules never stop a run. Every read from Central Context, by `rules.mjs` or by the connector, is shown to the person as a completed step, as the display guide says: nothing is read from Central Context without the person seeing that it was.
- **Replies.** Answer a card with its number or in words: `yes`, `y`, `sì`, `si`, `ok` and `va bene` mean `1`; `stop` and `basta` mean the card's Stop option. Read only the first word for this; a sentence that gives a result (and no number) is a typed answer.
- **Language.** Follow `${CLAUDE_PLUGIN_ROOT}/guides/language.md`: keep the person's language, also after a pick or a script's output. Write the cases in the ticket's language. Script output and cards keep their fixed words.
- **Never ask for a token**, key or password in the chat, and never show one.
- Refer to Jira tools by operation name on the Atlassian connector.
- Every script call runs from the project root: `node "${CLAUDE_PLUGIN_ROOT}/bin/<script>" …`. With `root` in the config the project root is that folder: every path the scripts print or take is relative to it, so the files you read and write are under it. Drop the machine lines (`TICKET_EVAL_JSON:`, `PROJECT_MISMATCH:`, `SIDE_JSON:`, `E2E_FOLDER_JSON:`, `RULES_JSON:`) when you show output.

## Steps

1. **Check.** With `--sync` in `$ARGUMENTS`, run only `node "${CLAUDE_PLUGIN_ROOT}/bin/xray.mjs" sync` (add the key when one follows `--sync`): it rewrites the per-ticket files from the CSV. Show its lines and stop. Otherwise the first `[A-Z][A-Z0-9_]*-\d+` in `$ARGUMENTS` is the key. No key: `pass a key: /quality-code:xray <KEY>`. Run `node "${CLAUDE_PLUGIN_ROOT}/bin/ticket.mjs" config check`. If it does not print `ok`, show its lines and stop (a missing config is never a dead end: show the **Not set up** card of the display guide). Xray is part of Jira, so no repo is needed: a personal setup (`ok (personal: …)`, for QA and PO) works, and so does any folder when the personal config exists. Read the config `config check` named (the project config (`ticket.mjs config check` shows where it is), else the personal one): `ticketsDir` (the path on the `tickets folder:` line `config check` printed, used as it is: where this person keeps the project's files, in the repo or outside it), `features` and the `xray` block. A repo config with no `xray` block: say `Xray test cases are off in this project: add an "xray" block to the project config.json (docs/GUIDE.md, "Xray test cases").` and stop. A personal config needs no `xray` block: the cases go to `xray-cases.csv` in its tickets folder and the per-ticket files beside the tickets.
   - **`--dry-run`:** go through steps 1 to 4 and show the plan card without its numbered options, then stop: no case written, nothing posted. The gate still saves the sanitized ticket (`<ticketsDir>/<KEY>/ticket.json`). A refused ticket ends the dry run at the gate's report: no refuse card, so no comment, fill-in or Jira update. **`--ci`:** never ask: a card that needs an answer stops the command instead (`--ci` stops here: <the question, in one line>), and step 4 writes without the card.

   Then read `${CLAUDE_PLUGIN_ROOT}/guides/connectors.md` and follow it, as the start command does. From the plugin settings (each empty when not set): `jira_email` is `${user_config.jira_email}`, `gitlab_username` is `${user_config.gitlab_username}`, `gitlab_api_url` is `${user_config.gitlab_api_url}`. Jira is required: go on only when its card lets you continue.
2. **Ticket and gate.** Read `${CLAUDE_PLUGIN_ROOT}/guides/ticket-eval.md` and follow its steps 1–5 with `<KEY>` as `$ARGUMENTS`, no flags: read, save, sanitize and score.
   - **Refused:** its refuse card and its style, as written there. Go on only when that flow ends with the ticket passing (the guided fill-in, then `1` or `2` on its Jira update card). Option 3 (continue anyway), a comment posted, a cancel or a stop: stop, `Xray test cases need a ticket that passes the gate.` Nothing written.
   - **Passed:** go on with `<ticketsDir>/<KEY>/ticket.json`, the only copy of the ticket; never edit it. Keep the `feature` and the `route` from the last `TICKET_EVAL_JSON:` line. The scenarios are the ticket's plus the QA plan's (`qaPlan.scenarios` in `ticket.json`), each name once; where both have a scenario with the same name, the ticket's wins.
   - **Fullstack:** a ticket whose `side` (the last `TICKET_EVAL_JSON:` line) is `backend` gets no Xray test cases: say `Xray test cases are written for frontend tickets (Playwright tests).` and stop.
   - **Source code links.** With the ticket's `getJiraIssueRemoteIssueLinks`, its description and its comments, collect the GitLab or GitHub links (merge requests, pull requests, branches, commits). Read each one read-only with the source code connector when it is connected: title, description, changed files and diff. In a repo, the local code of the branch is read as well. No repo is needed. When the source code connector is not connected, do not skip it silently: follow the **Merge requests found in a ticket** section of `${CLAUDE_PLUGIN_ROOT}/guides/connectors.md` (sign in with `/mcp`, or `/quality-code:setup`; `Signed in: read the merge requests`, `Continue without the code`, `Stop`); on `Continue without the code` the cases come from the ticket alone. A ticket with no such link says nothing about GitLab. What the code shows (a field validated, a role checked, an error message, an API call) becomes a case of its own when the ticket's scenarios do not cover it, marked `From the code` on the card. Never copy secrets or personal data from the code into a case.
3. **Screen.** A `--route PATH` in `$ARGUMENTS` is used as it is: it must start with `/` and be one line; otherwise say `--route must be a path in the app starting with /, like /orders` and stop. Without one, the `route` from step 2 is used, with no card. With neither, show `/quality-code:spec`'s screen card (its step 3, Playwright) and do as it says.
4. **Plan.** First search Central Context with the connector, as the Rules section says, and show it as a completed step: `Searched Central Context · "order list filters" · 5 rules, 1 applies`, `· none apply`, or `Searched Central Context · not connected ⚠️`. Then run `node "${CLAUDE_PLUGIN_ROOT}/bin/rules.mjs" --side frontend` and show its lines as printed, as completed steps, one per source. From its `RULES_JSON:` line (`rules`, Central Context's, `builtin.rules`, the plugin's, and `local.rules`, the team's) keep the rules that apply to the cases of this ticket, as the Rules section says, and add how many apply to each line: `Read from Central Context · 14 rules, 3 apply`, `Built-in rules · 2 drafts, 1 applies`, `Read from local rules · 3 rules, 1 applies`, or `, none apply`. Then read `${CLAUDE_PLUGIN_ROOT}/guides/playwright-writing.md` for its extra probes, then `playwright.guide` when it is set. One case per scenario, with the result it checks as a plain sentence from the ticket's Then. Then, unless `$ARGUMENTS` has `--no-extras`, at most 3 extra probes from the guide's list that apply to this screen, first the ones a rule that applies points at, one case each. Show this card and end the turn (cases from the source code links of step 2 are listed under `From the code`):

   ```
   Xray test cases for <KEY>, on <route>
     From the ticket
       <scenario, in a few words>
     Extra (not in the ticket)
       <extra check, in a few words>
   1. Write these test cases
   2. Leave out the extras
   3. No, I'll type the right result
   4. Stop
   ```

   With no extra probe, leave out the `Extra (not in the ticket)` lines and option 2, and number the rest in order. On `Leave out the extras`, drop them and show the card again. On `No, I'll type the right result`, ask `What should the result be?` and add the answer to the ticket as `ticket --eval`'s guided fill-in does (`ticket.mjs add --in @<ticketsDir>/<KEY>/ticket.json ac_present -- "<answer>"`; its Jira update card follows when it is accepted), then show the card again with the new result. On `Stop`, stop.
5. **Write.** Write `<ticketsDir>/<KEY>/xray.json`: a JSON list with one case per test, each scenario and each extra probe:

   ```
   { "key": "<the test's name>", "summary": "<what it checks, one sentence>", "ticket": "<KEY>",
     "feature": "<the feature label>", "steps": [{ "action": "…", "data": "…", "expected": "…" }] }
   ```

   - **key:** the Playwright test's name: the scenario's name for a scenario, `Extra: <what it probes>` for an extra probe, as `/quality-code:spec` names them. It links the case to its test.
   - **steps:** from the scenario's Gherkin, in order: each `Given` and `When` is an `action`, each `Then` the `expected` of the step before it. The first step opens the screen (`Open <route>`). `data` holds the values the step types or picks, only when there are any. An extra probe's steps are what it probes and the result the guide lets it expect.
   - **Leave out** what you do not know: `description`, `label`, `priority`, `epic`. `testType` is `Cucumber` unless the case has no Gherkin behind it (`Generic`).

   Then run `node "${CLAUDE_PLUGIN_ROOT}/bin/xray.mjs" add @<ticketsDir>/<KEY>/xray.json`. Exit 2 is a config or input error: show its lines; when it names a case, fix that case in `xray.json` once and run again.
6. **Report.** Show the script's lines as printed: the case numbers, a case that was already there, and the files for QA. Add one line: `QA imports the case file in Xray: Test Repository, Import, Excel or CSV.` Then the next step, which continues this work: `Next: /quality-code:qa runs these cases in the browser, test by test, and drafts the defects.` Nothing is graded and no test is written: say `/quality-code:spec <KEY>` writes the tests with the same names when you need them.

7. **Create them in Xray** (only when the plugin's `xray` connector offers `create_tests`, which means the Xray API key is set; otherwise stop at step 6). The tests are already in Xray's import file; this puts them in Xray itself. Skip it with `--dry-run` (show the card without its options) and with `--ci`. Run `node "${CLAUDE_PLUGIN_ROOT}/bin/xray.mjs" created <KEY>` and leave out the cases it already lists: they exist in Xray, and are never created twice. Nothing left: say `Every case of <KEY> is already in Xray.` and stop. Show this card and end the turn:

   ```
   Create <n> test(s) in Xray for [KEY](url)?
     <case name>: <steps> steps
   Project <project key>, linked to [KEY](url)<, and added to [RUN](url) when --run gave one>
   1. Create them in Xray
   2. Only the file, I import it myself
   3. Stop
   ```

   On `1`: call `create_tests` with the project (the key's project) and the cases (each `summary` and `steps` with `action`, `data` and `result` from `xray.json`, and the ticket key as its label). Never call it twice for the same cases: if it fails or says it is still running, show that and tell the tester to look in Xray's Test Repository before trying again. A result that is not ok can still list tests it created (`partially_successful`): record those as below, so a retry never creates them twice. For each test created, run `node "${CLAUDE_PLUGIN_ROOT}/bin/xray.mjs" created <KEY> add "<case name>" <TEST KEY>` (the case order matches `created[].index`). Then link each test to the ticket: from `listJiraIssueLinkTypes`, the link type named `Test` or `Tests` (ignoring case), with `createJiraIssueLink` (the ticket is tested by the test). With no such type, skip the links and say `No Test link type on this site: link them by hand if your team does.` With `--run <RUN KEY>` (a key), call `add_tests_to_test_execution` with it and the new test keys. Say which tests were created, as links. Nothing here runs a test or changes a status.

## Examples

- `/quality-code:xray ABC-123`: check the ticket is ready, plan the cases, write them for QA
- `/quality-code:xray ABC-123 --no-extras`: only the ticket's scenarios
- `/quality-code:xray ABC-123 --route /orders/new`: cases for this screen
- `/quality-code:xray ABC-123 --dry-run`: the readiness check and the plan, then stop; no case is written and nothing is posted
- `/quality-code:xray ABC-123 --run ABC-200`: with the Xray API key, also create the tests in Xray, link them to the ticket and add them to that test execution
- `/quality-code:xray --sync ABC-123`: rewrite the ticket's case.csv and case.xlsx from the CSV
