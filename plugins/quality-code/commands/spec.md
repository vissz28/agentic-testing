Takes a ticket to checked tests. You write the tests; the scripts gate the ticket and grade the tests. A person is asked three times at most: at the gate, only when the ticket is refused; at the plan; and at the read-back after the card. Everything else runs without stopping. Plain English, short sentences, numbered cards. Show every card and output the way `${CLAUDE_PLUGIN_ROOT}/guides/display.md` says: a section per step, tables, colour marks, and the picker for questions. Every question is asked with the AskUserQuestion picker as display.md says, never as a numbered text card; the text card is only for a client without the tool. End your turn after every card and wait for the answer.

The steps are the same for both adapters. Where a **Vitest** project (unit tests against a source file) and a **Playwright** project (e2e tests against a screen of the app) differ, the step says so. A **fullstack** project (`adapter: fullstack`) has both: a backend ticket takes the Vitest parts of each step, a frontend ticket the Playwright parts, and a fullstack ticket both, the Vitest part first. Its specs are checked together, in one run (step 6).

The backend runner is the one the config names: `adapter` on a backend project, `backend` (default `vitest`) on a fullstack one. It is Vitest, pytest, JUnit, Go or .NET (`vitest`, `pytest`, `junit`, `go`, `dotnet`). Wherever a step below says **Vitest** for the backend, it means the backend runner (Vitest, pytest, JUnit, Go or .NET): its layers, its writing guide and its test file names; the seed builders are Vitest's alone, and the pipeline takes `--target '<target>'` (Stryker) only on Vitest: on another backend runner leave it out of the pipeline run (the target is still the code the tests check).

## Rules

- **Where files go.** When the command has ended (after its last card is answered, or its last step when it shows none), follow `${CLAUDE_PLUGIN_ROOT}/guides/save-place.md`: the first run of a project asks once where its files and logs are kept.
- **Run each plugin script exactly as written:** one `node "${CLAUDE_PLUGIN_ROOT}/bin/…"` command per call, with nothing added before or after it (no `echo`, `;`, `&&`, `|` or redirection). The tool result already shows a non-zero exit code. Anything added stops the call from matching its pre-approval and costs a permission prompt.
- **Where you stopped.** Read `${CLAUDE_PLUGIN_ROOT}/guides/progress.md` and follow it with the command `spec` and the ticket's `--key`, once step 2 has the key: ask to go on from the last step at the start, and save after each step that took an answer. Steps and answers to save: step 2 `side` and `flow`; step 3 `target` (a path or a route) and `layers`; step 4 `plan` (the layers per scenario, not the ticket text) once the plan card is answered; step 5 `written` (the spec paths). The plan card is always shown again before anything is written. Clear it after step 9. The same guide's **Project context** section also applies: reuse the saved `flow`, `tests` (with the test home), `style`, `stack`, `base` and `connectors` while they are fresh, record the target and the written specs with `context file`, and `--fresh` reads everything again.
- **The scripts decide.** `ticket.mjs` scores the ticket; the pipeline grades the tests. Never compute, change or soften a score, a verdict or a count, and never say a test is good yourself.
- **Never edit application code.** Write only spec files, only in the layer folders (Vitest) or the e2e folder (Playwright). Source files, config and other tests stay as they are. If the boundary hook denies a write, read its reason and write in a test folder instead.
- **The project's runner.** `runners` in the config names it when it is not Vitest or Playwright: `runners.unit` (`jest`, `mocha`, or `node` for Node's own `node --test`) takes every Vitest part of the steps below, `runners.e2e` (`cypress`) every Playwright part. Write the tests in that runner, the way the specs already there do: Jest's `jest.fn`, `jest.mock` and `jest.useFakeTimers`; Mocha's Chai, `expect(x).to.equal(…)`; node --test's `node:test` (`describe`, `it`, `mock.fn`) and `node:assert/strict` (`assert.strictEqual(total, 108)`); Cypress's `cy.visit`, `cy.get(…).should(…)` and `cy.intercept`. Mocha and Cypress have no todo: a behaviour the ticket does not pin down gets no test, and the plan names it. The pipeline runs that runner with the generic checks, and its card says so.
- **Replies.** Answer a card with its number or in words: `yes`, `y`, `sì`, `si`, `ok` and `va bene` mean `1`; `no`, `stop` and `basta` mean the card's No, Stop or Cancel option; on the plan card, a sentence that asks for another change (not a number, not a result) means `Something else`. Read only the first word for this; a sentence that gives a result (and no number) is a typed answer.
- **Language.** Follow `${CLAUDE_PLUGIN_ROOT}/guides/language.md`: keep the person's language, also after a pick or a script's output. Before they write a sentence, the ticket's language (Italian for an Italian ticket). Script output and cards keep their fixed words.
- **Never weaken or delete a test** to make a check pass: no removed `expect`, no looser matcher, no `.skip`, no deleted `it` or `test`.
- **Never ask for a token**, key or password in the chat, and never show one.
- Refer to Jira tools by operation name on the Atlassian connector.
- Every script call runs from the project root: `node "${CLAUDE_PLUGIN_ROOT}/bin/<script>" …`. With `root` in `.claude/quality-code.json` the project root is that folder: every path the scripts print or take is relative to it, so the files you read and write are under it. Drop the machine lines (`BRANCH_JSON:`, `MERGED_JSON:`, `TICKET_EVAL_JSON:`, `GATE_JSON:`, `SAVED_JSON:`, `E2E_FOLDER_JSON:`, `RULES_JSON:`, `PIPELINE_JSON:`) when you show output.
- **Central Context rules.** The company's testing rules come from its Central Context hub: step 4 reads the ones for the ticket's side with `rules.mjs`, which picks them (the active rules of the quality domain about testing whose `applies_to` fits the side), it also reads the plugin's built-in rules (drafts the plugin ships until Central Context publishes them) and, with `centralContext.local` in the config, the team's own rules from that folder. One id is one rule: the team's wins, then Central Context's, then the built-in one, and `rules.mjs` has already dropped the others. Every list is candidates, never orders: apply only the rules that bear on the tests you write for this ticket, from any list, for example isolated tests with stubs for external dependencies. A rule about something else (a test strategy document, a tracking tool, a coverage target for CI) does not apply to writing these tests: leave it out. Where two rules disagree, the team's own wins, then Central Context's, then the built-in one. A rule never gives an expected value, never outranks the ticket's Then or a team guide, and never changes a score or a check. Never paste rule text into a spec or Jira. When `rules.mjs` reads none (no hub, or it does not answer), go on without them: the rules never stop a run. `rules.mjs` reads the testing rules; the `central-context` connector searches Central Context for the ticket's own topic. Step 4 always starts with that search: `search_knowledge` with what the code under test does in a few English words (`decimal quantity formatting`, `access token check`; English ranks best, even for an Italian ticket), no `domain`, `max_results` 5, and `client_context` the project folder's name, `#` and the key, with no space (`shop#ABC-123`: Central Context refuses spaces), which Central Context records. A second search only for a topic the ticket touches that the first missed (input checks, auth, secrets, data access, an API contract), never more. Read each hit's summary: a hit that bears on the tests you write is a candidate like the others, and you read it with `get_knowledge_document` (the same `client_context`) before you apply it; a hit that does not, or no hit at all, is dropped, and the run goes on with the rules `rules.mjs` reads. A hit `rules.mjs` also reads is one rule. Those rules are candidates the same way, and the team's own rules still win. Without the connector, the search is skipped and said so. Every read from Central Context, by `rules.mjs` or by the connector, is shown to the person as a completed step, as the display guide says: nothing is read from Central Context without the person seeing that it was.
- **Run marker.** Once `run start` has succeeded, every way out of this command runs `node "${CLAUDE_PLUGIN_ROOT}/bin/checks.mjs" run stop` first: the card, a stop, an error, a crash of a script. `run stop` is safe to run twice.

## Examples

- `/quality-code:spec`: the ticket of this branch: gate, plan, write and check
- `/quality-code:spec ABC-123`: gate the ticket, pick the code or the screen, plan, write and check
- `/quality-code:spec ABC-123 --gate-only`: the gate alone, as `/quality-code:ticket-eval ABC-123`
- `/quality-code:spec ABC-123 --yes`: no plan question
- `/quality-code:spec ABC-123 --layer unit`: Vitest, write only in the `unit` layer
- `/quality-code:spec ABC-123 --target src/pricing.ts`: Vitest, skip the target card
- `/quality-code:spec ABC-123 --route /orders/new`: Playwright, test this screen
- `/quality-code:spec ABC-123 --no-extras`: Playwright, only the ticket's scenarios
- `/quality-code:spec ABC-123 --no-axe`: Playwright, without the accessibility scan
- `/quality-code:spec ABC-123 --target src/pricing.ts --route /orders`: fullstack, a backend target and a screen
- `/quality-code:spec ABC-123 --dry-run`: the gate and the plan, then stop; no test is written and nothing is posted
- `/quality-code:spec ABC-123 --ci`: no questions; stops where it would have to ask
